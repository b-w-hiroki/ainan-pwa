# 仕様・設計の更新ワークフロー

更新日: 2026-10-19。機能や構造を更新するたび、コードと同じPRで文書の更新要否を決める。

## 文書の役割

| 場所 | 書く内容 |
| --- | --- |
| [現行仕様書](PRODUCT_SPEC.md) | ユーザーが現在体験できる振る舞い、制約、完了判定 |
| [現行技術設計書](TECHNICAL_DESIGN.md) | 実装の構成、責務、データ・アセットの契約、検証ゲート |
| `docs/design/` | 個別機能の詳細設計や将来案。現行実装か提案かを明示 |
| GitHub Issue | 最新の判断、作業状態、ブロック、承認証跡。特に素材は [#216](https://github.com/b-w-hiroki/ainan-pwa/issues/216) |
| コードとテスト | 実際の挙動と検証可能な契約 |

固定バックログや設計案の本文を現行仕様へそのまま移さない。数値・素材候補のように頻繁に変わる情報は正本へリンクし、二重管理を避ける。文書と実装が食い違ったら、意図した振る舞いをIssue/PRで確定し、同じPRで整合させる。

## 変更ごとの手順

1. 作業開始時に最新main、関連Issue、現行仕様書・設計書を読む。
2. PRを作る前に差分を分類し、本文へ `Docs impact: product|design|both|none` と `Docs rationale: ...` を1行ずつ記入する。
3. ユーザーに見える振る舞い、導線、操作、結果、対応端末、リリース条件が変わるなら `product` とし、`docs/PRODUCT_SPEC.md` を同じPRで更新する。
4. 構造、責務、保存schema、描画owner、アセット契約、検証・配信手順が変わるなら `design` とし、`docs/TECHNICAL_DESIGN.md` を同じPRで更新する。両方なら `both`。
5. 文言・画像の微修正、テストだけの修正など、両文書の意味が変わらない場合は `none` とし、理由に変更箇所と非影響の根拠を書く。単に「不要」とは書かない。
6. 関連する詳細設計、操作説明、図、IssueのDone状態も必要に応じて更新する。現行文書の更新だけで承認や実機QAを代用しない。
7. 変更に適したsmoke、`npm run build`、必要な実ブラウザQAを実施し、PRのValidationへ実測を記入する。レビューで文書と動作を一緒に確認してからマージする。

`CI` の文書同期チェックは、製品コード・設定・アセットを変えるPRで上記2行を要求し、`product` / `design` / `both` の場合は対応する正本ファイルの差分も要求する。`none` には具体的な理由が必要。CIは内容の正しさを判定できないため、レビューで実装との整合を確認する。

## 更新時の書き方

- 既に提供している機能は現在形で、未完了・QA専用・提案は明記する。
- 変更前後のユーザー体験と、守るべき互換性・失敗時の動作を書く。
- 設計書は「どの層が責任を持つか」「何で検証するか」を更新する。関数名だけの羅列にしない。
- 数値やIssue状態を写すときは日付を付け、最新状態を主張する文は正本へリンクする。
- 新しい画面や保存形式が増えたら、図と関連ファイルの参照も見直す。

文書のみのPRは自動チェックの対象外だが、リンクと記述が最新mainに合うことをレビューする。
